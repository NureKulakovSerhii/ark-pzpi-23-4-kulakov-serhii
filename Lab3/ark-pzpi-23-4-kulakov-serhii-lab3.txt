	3 ОПИС ВИКОНАННОЇЇ РОБОТИ
	У процесі розробки серверної частини програмної системи було використано багатошарову архітектуру, що забезпечує чіткий розподіл відповідальностей між компонентами системи, підвищує її підтримуваність, масштабованність та спрощує тестування.
	Архітектура системи складається з чотирьох основних логічних шарів: Domain, Data, Services, API.
	Шар Domain відповідає за опис предметної системи. У цьому шарі зосереджені сутності, DTO-об’єкти, перерахування(enums), а також абстракції у вигляді інтерфейсів, що реалізуються у шарах Data і Sevices. Domain шар не містить залежностей від конкретних технологій доступу до даних або зовнішніх сервісів, що забезпечує незалежність бізнес-моделі від реалізації.
	Шар Data призначений для роботи з базою даних та реалізує доступ до даних за допомогою Entity Framework Core. У цьому шарі створено контекст бази даних, конфігурації для створення кожної сутності(де описані зв’язки сутностей одна з одною), зберігаються міграції, а також реалізовуються репозиторії. Репозиторії інкапсулюють логіку взаємодії з базою даних і виконують лише CRUD-операції та запити, що не містять бізнес логіки. Такий пдхід дозволяє ізолювати роботу з даними від інших частин системи.
	Шар Services реалізує бізнес-логіку програмної системи. Саме тут виконуються перевірки бізнес-правил, валідація даних, взаємодія  між кількома репозиторіями та робота із зовнішними сервісами, наприклад, сервісом Cloudinary, що використовується у проекті для зберігання користувацьких зображень. Сервіси використовують інтерфейси репозиторіїв, що дозволяє дотримуватись принципу інверсії залежностей. Додатково в цьому шарі реалізовано допоміжні компоненти (Helpers), зокрема маппери для перетворення сутностей у DTO та статичні класи для сортування й обробки даних.
	Шар API є зовнішнім рівнем взаємодії з системою та реалізований у вигляді ASP.NET Core Web API. У цьому шарі розташовані контролери, файл Program.cs, а також інші конфігураційні файли, необхадні для запуску та роботи вебзастосунку. Контролери відповідають за обробку запитів клієнтів, виклик відповідних сервісів та повернення результатів. У межах проекту реалізовано чотири контролери: 
　　　　- AdvertController для управління оголошеннями, 	  
　　　　- AuthController для автентифікації та авторизації користувачів, 	- ProfileController для управління профілем користувача та 	   	- SupportController для роботи зі зверненнями служби підтримки.
　　　　Опис реалізації бізнес логіки
　　　　Реалізація бізнес-логіки серверної частини системи побудована на паттерну “репозиторій + сервіс”. Репозиторії інкапсулюють доступ до бази даних і виконують CRUD-операції та запити, не містячи бізнес логіки. Сервіси використовують репозиторії для взаємодії з даними та реалізують усі правила бізнес-логіки, перевірку даних, валідацію, а також роботу з зовнішніми сервісами. Кожен сервіс містить методи, які відповідають за конкретні операції у системі.
　　　　Сервіс AdvertService реалізує бізнес-логіку, пов’язану з управліннями оголошеннями, та опирається на три репозиторії:
　　　　- IAdvertRepository - доступ даних до оголошень, CRUD-операції та запити до таблиці Adverts;
　　　　- IUserRepository - доступ до даних користувачив, що необхідні для перевірки прав та зв’язку оголошень з користувачами;
　　　　- IWarehouseRepository - забезпечує роботу з даними складів, пов’язаних з оголошеннями;
　　　　Сервіс забезпечує:
- Створення нових оголошень з перевіркою даних користувача та валідацією інформації;
- Оновлення існуючих оголошень із урахуванням правил бізнес-логіки;
- Видалення оголошень із контролем прав користувача або модератора та пов’язаними складами;
- Приховування та активацію оголошень для контролю їх видимості;
- Пошук оголошень та складів за критеріями користувача;
- Сортування оголошень за різними параметрами;
- Управління пов’язаними складами, включно із завантаженням та видаленням зображень у зовнішньому сервісі Cloudinary.
- Перетворення сутностей у DTO та інші допоміжні обробки за допомогою мапперів статичних класів.
	Сервіс CommentService реалізує логіку для роботи з коментарями у систем підтримки, використовує репозиторії ICommentRepository, ITicketRepository, IUserRepository. Функціонал:
- Створення нового коментаря до тікета;
- Оновлення статусу тікета при першій відповіді модераторі;
- Отримання конкретного коментаря, отримання всіх коментарів, пов’язаних з певним тікетом.
	Сервіс FavoriteService відповідає за реалізацію функціоналу улюблених оголошень користувача. Він використовує репозиторії IAdvertRepository і IUserRepository. Функціонал:
- Додавання оголошення до списку обраних з перевіркою існування користувача та оголошення;
- Отримання списку обраних користувача, з фільтрацією лише активних оголошень;
- Видалення оголошення з списку обраних із попередньою перевіркою наявності цього оголошення у списку;
- Забезпечення логіки порядку додавання оголошень у список обраних для зручного відображення користувачу.
	Сервіс ProfileService реалізує управління профілем користувача. Використовує репозиторії IProfileRepository і IUserRepository, а також AutoMapper для перетворення сутностей у DTO. Функціонал:
- Отримання даних користувача за його Id;
- Оновлення інформації профілю користувача;
- Використання маппера для перетворення сутностей User у DTO для зручного відображення у клієнтській частині.
　　　　Сервіс TicketService реалізує логіку для роботи зі зверненнями користувачів до служби підтримки. Використовує репозиторії ITicketRepository і IUserRepository. Функціонал:
- Створення нового ттікета з присвоєнням статусу Open;
- Видалення тікета із перевіркою його існування в БД;
- Призначення тікета модератору з перевіркою ролей користувача та зміною статуса тікета на InProgress;
- Закриття тікета користувачем із перевіркою прав на його закриття та оновленням статусу на Closed;
- Отримання списку всіх відкритих тікетів;
- Використання маппера для перетворення сутностей SupportTicket у відповідні DTO для передачі клієнтській частині.
	Сервіс UserService відповідає за управління користувачами та авторизацію у системі, використовує репозиторій IUserRepository. Функціонал:
- Реєстрація користувачів із хешуванням паролів;
- Авторизація користувачів із перевіркою логін і пароля та генерацію JWT і refresh-токенів;
- Оновлення JWT і refresh-токенів;
- Призначення користувачу роль модератора;
- Видалення refresh-токена при виході з системи;
- Вихід користувача із системи. 
	Роль модератора у системі наділяє користувача розширенними повноваженнями для контролю контенту платформи, зокрема для активації та деактивації оголошень у разі виявлення недоречного або такого, що поришує правила, змісту. Крім того, модератор забезпечує підтримку користувачів шляхом  опрацювання звернень та скарг, а також виконує аналіз роботи системи на основі статистичних даних і запитів.

	Математичні методи обробки даних.
	У серверній частині системи реалізовано математичну обробку даних у рамках бізнес-логіки. Основні напрями:
- Сортування оголошень: Для зручного відображення оголошень користувачу використовується статичний клас AdvertSortingExtensions, який на основі параметра сортування обирає потрібний порядок елементів (Програмний код наведено у Додатку Б.1)
	Цей метод використовується у сервісі AdvertService для сортування оголошень після вибірки з бази даних (Програмний код наведено у Додатку Б.2)
- Фільтрація та обчислення значень. Пошук складів та оголошень за критеріями користувача (Програмний код наведено у Додатку Б.3). Валідація числових значень, наприклад ціни чи площу (Програмний код наведено у Додатку Б.4)
- Аналітична обробка даних: підрахунок кількості активних оголошень, статистичний аналіз складів або рейтингових показників (Програмний код наведено у Додатку Б.5).
- Обмеження кількості улюблених оголошень: Перевірка на максимальну кількість (limit = 9) (Програмний код наведено у Додатку Б.6)
- Фільтрація активних оголошень: Під час отримання списку улюблених виконіється фільтрація (Програмний код наведено у Додатку 7)
	Таким чином, бізнес-логіка системи забезпечує:
- Сортування та фільтрацію даних оголошень;
- Перевірку та валідацію числових параметрів;
- Підрахунок статистичних показників для контролю бізнес-процесів;
- Обмеження та контроль кількості об’єктів у користувацьких списках для дотримання правил системи.

 public static class AdvertSotingExtensions
 {
     public static IEnumerable<AdvertDto> ApplySorting(this IEnumerable<AdvertDto> adverts, AdvertSortBy sortBy)
     {
         return sortBy switch
         {
             AdvertSortBy.PriceAsc => adverts.OrderBy(a => a.Warehouse.PricePerMonth),
             AdvertSortBy.PriceDesc => adverts.OrderByDescending(a => a.Warehouse.PricePerMonth),
             AdvertSortBy.ScaleAsc => adverts.OrderBy(a => a.Warehouse.Scale),
             AdvertSortBy.ScaleDesc => adverts.OrderByDescending(a => a.Warehouse.Scale),
             AdvertSortBy.FloorAsc => adverts.OrderBy(a => a.Warehouse.Floor),
             AdvertSortBy.FloorDesc => adverts.OrderByDescending(a => a.Warehouse.Floor),
             _ => adverts
         };
     }
 }

 public async Task<List<AdvertDto>>? SearchWarehouses(SearchWarehouseDto searchWarehouseDto, AdvertSortBy sortBy)
 {
     var warehouses = await warehouseRepository.SearchWarehouses(searchWarehouseDto);
     if (!warehouses.Any())
     {
         return new List<AdvertDto>();
     }
     var adverts = warehouses.SelectMany(w => w.Adverts).Select(advert => MapToAdvertDto(advert, advert.Warehouse, advert.User))
         .ApplySorting(sortBy)
         .ToList();
     return adverts;
 }
